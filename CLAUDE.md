# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

AoSPy computes expected-damage combat statistics for Age of Sigmar 4th edition armies. It stores armies/units/weapons/compositions in a local DuckDB file and exposes a French-language CLI (`aospy`) for querying duels, benchmarks, and full-army battle simulations. Domain text (docstrings, CLI help, output) is in French; keep new docstrings/help text in French for consistency.

## Setup & commands

```bash
pip install -e ".[dev]"        # editable install with pytest
pip install -e ".[analysis]"   # + pandas/statsmodels, only needed for `aospy cost ...`
pip install -e ".[gui]"        # + streamlit (implies [analysis]), only needed for the bonus simulator
pip install -e ".[roster]"     # + reportlab/pypdf, only needed for `aospy roster pdf`
python -m aospy <command>      # or `aospy <command>` once installed
streamlit run src/aospy/bonus_simulator/app.py   # bonus "what-if" simulator — see src/aospy/bonus_simulator/README.md
```

Run tests:

```bash
pytest                                       # full suite
pytest tests/engine/test_combat.py           # single file
pytest tests/engine/test_combat.py::test_prob_x_plus_basic   # single test
```

There is no configured linter; there is no `pytest.ini`/`tool.pytest.ini_options` in `pyproject.toml`, so pytest defaults apply (run from repo root). `tests/` mirrors the `src/aospy/` sub-package layout below.

Common CLI flows (all take `--db path/to.duckdb`, default `data/aospy.duckdb`):

```bash
aospy init                                  # create schema + seed data/armies.json (+ compositions.json)
aospy reset                                 # delete the DB file
aospy import bsdata --army "Stormcast Eternals"   # pull a live army from BSData (GitHub)
aospy import bsdata --all                   # import every known army
aospy import wahapedia --faction "Stormcast Eternals"   # import from Wahapedia CSV instead
aospy import wahapedia --all                # import every known faction (data/wahapedia/*.csv)
aospy unit duel --attacker X --defender Y
aospy unit benchmark --attacker X --charge a --detail
aospy unit benchmark-all --charge both -v   # persists all attacker×defender pairs to unit_benchmark
aospy unit benchmark-all --charge both --attacker-mode floor95 --defender-mode floor95   # same, but persists the 95%-confidence floor instead of the mean
aospy unit benchmark-all --charge both --attacker-mode floor80 --defender-mode mean      # asymmetric: A→B at the 80%-confidence floor, B→A at the mean
aospy unit stats --attacker X [--charge]    # mean / std / 95%-confidence damage floor vs 3 standard targets
aospy battle simulate --a <comp_id> --b <comp_id> --charge both
aospy import bsdata --all --clean-stale     # also purges units an import no longer touched (see `imported_at`)
aospy import wahapedia --all --clean-stale  # same, for the Wahapedia importer
aospy cost fit [--segmented]                # OLS points ~ features (needs `[analysis]`)
aospy cost residuals --top 20 --direction under   # most under/over-costed units by residual
aospy roster pdf --list "data/Proposition de listes/LRL L3 Avengers Wardens.txt"   # tournament PDF (needs `[roster]`)
aospy roster pdf --list "data/Proposition de listes/LRL L3 Avengers Wardens.txt" --mode fr   # same, French-verbatim mode (see "Roster modes" below)
```

`cost_model.fit_cost_model_factorial` (single OLS with categorical factors + hero/troupe interaction terms) is available as a library call but not yet wired to the CLI — see "Cost model" below.

## Architecture

`src/aospy/` is one sub-package per layer, bottom to top — each layer only calls downward. Each sub-package's own docstring (`__init__.py`) gives the one-line summary; this list adds the cross-file wiring:

1. **`domain/models.py`** — frozen/plain dataclasses (`Army`, `Weapon`, `Unit`, `HeroicTrait`, `Artefact`, `CompositionUnit`, `Composition`). No DB or logic.
2. **`persistence/db.py`** — opens a DuckDB connection at `DEFAULT_DB_PATH` (`data/aospy.duckdb`) and applies `persistence/schema.sql` on every `connect()` (idempotent `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` migrations). Schema changes go in `schema.sql`, not in Python.
3. **`persistence/repository.py`** — all SQL lives here; nothing above this layer writes raw SQL. `Unit.keywords` (`frozenset[str]`) round-trips through one comma-joined `VARCHAR` column.
4. **`engine/combat.py`** — pure math, no DB access. `expected_weapon_damage` (hit → wound → save/rend → ward, crit variants + intrinsic `Anti-X`/`Charge` bonuses parsed from `Weapon.abilities` — see "Intrinsic Anti-X/Charge bonuses" below) and its `E[D²]` twin `weapon_damage_moments` (→ `unit_damage_moments`). Damage-floor reads go through the *exact* discrete distribution (`weapon_damage_distribution` → `unit_damage_distribution` → `distribution_floor`), not a Gaussian approximation — see "Damage floor: exact distribution vs Gaussian approximation" below; `damage_floor66`/`80`/`95` (`mean − z·σ`) survive only as a comparison baseline. **Caveat**: `Weapon.attacks`/`damage` are integers resolved at import time (no dice notation kept), so variance only captures hit/wound/save/ward/crit randomness, not dice-valued attacks/damage.
5. **`engine/loadout.py`** — ported from StatHammer's `loadout.py`: parses `Unit.description` (free text) into per-weapon-profile model counts (`model_counts`). Best-effort, unrecognized clauses fall back to "every model carries every profile" (logged in the returned notes). Used by `combat.py::_effective_counts`.
6. **`orchestration/benchmark.py`** / **`orchestration/simulation.py`** — orchestration on `combat.py` + `repository.py`. `benchmark.py`: single-attacker-vs-many-defenders duels (`unit_duel`, `benchmark_attacker`, `run_all_benchmarks`), with independent `mode_a`/`mode_b: DamageMode` (`"mean"`/`"floor66"`/`"floor80"`/`"floor95"`) per duel direction — a duel need not read both sides at the same confidence level. `_attack_damage` reads `floorNN` modes off `combat.py::unit_damage_distribution`'s exact PMF (`distribution_floor`), not a Gaussian approximation. `simulation.py`: full composition-vs-composition (`simulate_battle`, all-entries-vs-all-entries).
7. **`cli/report.py`** — pure text formatting of `DuelResult`/`BattleReport`/unit-stats rows. No computation.
8. **`cli/__init__.py`** (argparse wiring, exposes `main`) / **`cli/commands.py`** (one `cmd_*` per subcommand, each opens its own DB connection via `_connect(args)` and closes it before returning).
9. **`importers/bsdata.py`** — downloads `.cat` XML from `BSData/age-of-sigmar-4th` (GitHub), parses BattleScribe profiles, upserts via `repository.replace_unit`. `KNOWN_ARMIES` maps army name → (catalogue, library, grand alliance). `Unit.description` is left `None` (no BattleScribe equivalent found yet — BSData units keep the `wielders`-based allocation instead). Filters Legends/expired content and merges free companion units into their paid parent — see the two dedicated sections below.
10. **`importers/wahapedia.py`** — second importer, reading `data/wahapedia/*.csv` into the *same* schema via the same `repository.replace_unit`. Reuses `bsdata.parse_dice`/`parse_target`/`KNOWN_ARMIES`. See "Wahapedia import" below.
11. **`analysis/features.py`** / **`analysis/cost_model.py`** (needs `[analysis]`: pandas + statsmodels). `features.py::compute_features` probes a unit against three synthetic defenders (save 2+/4+/none) via `combat.py`'s moments engine → `UnitFeatures`. `cost_model.py` regresses `points ~ features` (OLS) three ways (`fit_cost_model`, `fit_segmented`, `fit_cost_model_factorial`) for coefficients + per-unit residuals. See "Cost model" below.
12. **`persistence/seed.py`** — one-time JSON loaders (`data/armies.json`, `data/compositions.json`), idempotent by name.
13. **`bonus_simulator/`** (needs `[gui]`: streamlit, implies `[analysis]`) — self-contained: engine (`bonus.py`), orchestration (`whatif.py`) and Streamlit UI (`app.py`/`army_rules.py`) for this one feature all live together here rather than split across `engine/`/`orchestration/`/a UI package, since none of it is reused elsewhere. Live "what-if" bonus simulator — see "Bonus simulator" below and `bonus_simulator/README.md` for the user guide.
14. **`tournament_kit/`** (needs `[roster]`: reportlab + pypdf) — self-contained, no DB access. Compiles a raw army-list export + its battletome unit profiles into one tournament-ready PDF. See "Tournament kit" below.

### Key domain concepts

- **Points economy**: every `DuelResult` computes `pts_destroyed`/`pts_lost`/`pts_net`/`roi` by scaling expected damage against the defender's/attacker's total points — units are compared across point costs, not just raw damage.
- **Reinforcement**: doubles model count and points; `combat.py::_effective_counts` scales per-profile model counts (from `loadout.model_counts` or `weapon.wielders`) proportionally rather than assuming all models carry all weapons.
- **Side modifiers**: All-out Attack (+1 hit) / All-out Defense (+1 save) are `CombatModifiers`/`SideOptions`, threaded as directional flags (`--aoa`/`--aod`). Charge (`--charge {a,b,both,none}`) carries **no universal bonus** in AoS4 — only a weapon's own `Charge (+N <Stat>)` ability text does (see "Intrinsic Anti-X/Charge bonuses" below).
- **`unit_benchmark` table**: persisted duel-result cache keyed by `(attacker_id, defender_id, attacker_reinforced, defender_reinforced, attacker_charged, defender_charged, attacker_mode, defender_mode)`, populated via `benchmark-all`. `attacker_mode`/`defender_mode` (`"mean"`/`"floor66"`/`"floor80"`/`"floor95"`) let different confidence levels coexist per duel direction — see `orchestration/benchmark.py::DamageMode`. `repository.save_benchmark_results_many` batches upserts through a staged temp table (DuckDB `executemany` is ~150ms/row vs <2ms/row for an inlined multi-row `INSERT`).
- **BSData `wielders`**: inferred from BattleScribe `constraints` on `selections` (min/max, scoped to `parent` or the unit), with parent-resolved counts for nested weapon bundles, replaced-base-weapon reduction, and group-level exclusive choices — see "BSData wielders resolution" below. Trickiest part of that importer; check there first if imported weapon counts look wrong.

### Wahapedia import — second import mechanism, same schema

`data/wahapedia/*.csv` (pipe-separated, UTF-8 BOM) is an alternative to BSData; both write into the identical schema, so downstream code doesn't care which importer populated a given army. Deliberate simplifications:

- **`Weapon.wielders` is always `0`** ("all models carry it"). Instead, `Unit.description` (the warscroll's free-text restriction) is captured and resolved at combat-time by `loadout.model_counts`.
- **`Unit.keywords`** captured in full (not just `HERO`) so weapon-level `Anti-<KEYWORD>` clauses can be evaluated against a defender's keyword set.
- **Only "regular battlefield unit" roles** are imported (`INGESTIBLE_ROLES`: Infantry/Cavalry/Beast/Monster/War Machine, plain or `* Hero`); `Endless Spell`/`Manifestation`/`Regiment of Renown`/`Faction Terrain` are skipped (`Unit` has no `role` column to store them distinctly).
- **Canonical dedup** (`_canonical_ids`, ported from StatHammer's `mark_canonical`): a warscroll "shell" dominated by a sibling (`virtual='false'` version, or a non-RoR version) is dropped. No manual overrides file — a residual ambiguity just picks the first candidate and warns, so `--all` never blocks.
- **Grand alliance mapping** (`FACTION_GRAND_ALLIANCE`) is derived from `bsdata.KNOWN_ARMIES` (faction names match) since Wahapedia CSVs carry no alliance info.

### Legends & stale-unit filtering (both importers)

- **Legends detection**: `bsdata._is_legends_catalogue` skips a whole catalogue named `... [Legends]`. For individually-retired units in an otherwise-current army, `bsdata._wahapedia_legends_names` cross-references `data/wahapedia/Source.csv`+`Warscrolls.csv` by name (read-only; `bsdata.py` never imports `wahapedia.py`, keeping the one-way dependency above) — same "legend" substring match `wahapedia._legends_warscroll_ids` uses for its own importer.
- **Expired narrative packs**: `bsdata._is_expired_variant` matches the name suffix "Scourge of Ghyran" (current seasonal narrative pack, absent from matched-play rules); shared by both importers. Both count these on `ImportSummary.skipped_legends`, reported separately from `skipped_no_profile`/`skipped_no_points`. "Scourge of Aqshy" (an earlier pack) is deliberately *not* filtered — those BSData entries target a distinct `targetId`/points cost from the base unit, so they're standalone valid units, not duplicates.
- **`--clean-stale`** (`cmd_import_bsdata`/`cmd_import_wahapedia`): records `datetime.now()` as `cutoff` before importing, then `repository.delete_units_imported_before(con, cutoff, army_id=...)` deletes any unit (+ weapons/composition entries/`unit_benchmark` rows) whose `unit.imported_at` predates it — i.e. units the run didn't touch. Scoped to the current army/faction, unscoped for `--all`.
- **Why `imported_at`/`unit_benchmark.attacker_mode`/`defender_mode` are declared directly in `CREATE TABLE`** rather than via the usual `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` migration: DuckDB silently resets a column's value to its `DEFAULT` if that statement re-runs on a column that already exists — which would wipe `imported_at` (or mislabel old mode rows) on every `connect()`. This column pair has been through two migrations, both one-shot table rewrites in `db.py::connect()`: `floor80` (BOOLEAN) → `floor95` (BOOLEAN, confidence level moved 80%→95%, `_migrate_floor95` purges leftover `floor95=TRUE` rows from the old formula) → `attacker_mode`/`defender_mode` (VARCHAR, `_migrate_damage_mode` rebuilds the table so each duel direction can read a different confidence level, translating old `floor95` values 1:1 with no data loss).

### Composite/companion unit merging (`bsdata.py` only)

Some warscrolls are split across several free BattleScribe entries that only exist because a paid entry was taken (e.g. "Neave Blacktalon" + Neave's Companions, "Morathi-Khaine" + The Shadow Queen, "Freeguild Command Corps" = paid Adjutants + free Auxiliaries). `_detect_composite_units` finds these by following the BSData `entryLink`/`condition` graph itself (a free entry's condition referencing another, paid `entryLink`) rather than a hardcoded name list — verified against all 27 known catalogues (7 sub-entries across 4 armies). `_merge_composite_units` then folds the free entry's models/weapons/keywords into its paid parent in-place. **Simplification**: if the two differ in `save`, the parent's value wins (aospy's `Unit` has one `save` per unit).

Wahapedia's importer has no equivalent merge — companion warscrolls there still land as separate `points <= 0` rows, which is why `analysis/features.py::feature_frame` unconditionally excludes `points <= 0` units from training/scoring (mechanically ≈ -100% residual otherwise, not a meaningful signal).

### BSData wielders resolution (`_extract_weapons`/`_weapon_wielders` in `bsdata.py`)

`_extract_weapons`'s `walk` resolves `model_count` **top-down**: each parent computes how many times *its own* children are actually picked (via `_raw_wielders`) before recursing, rather than threading the top-level unit size unchanged all the way down. This matters for three BattleScribe patterns that a flat "min/max scope=parent" read gets wrong:

- **Nested weapon bundles** (e.g. Kharadron Overlords' Endrinriggers "Skyrigger Heavy Weapon and Gun Butt", capped 1/3 models at the unit): the wrapper's own unit-wide cap must be resolved and passed down as the new `model_count` for its two sub-weapons, or they'd inherit the full unit size instead of the wrapper's cap.
- **Base weapon replaced by an upgrade** (`_replaced_by`): BattleScribe encodes "N models can replace their base weapon(s) with X" as a modifier that sets the base weapon's own min/max constraint to 0, conditioned on the replacement's selection. `_replaced_by` reads that modifier back off the base weapon entry and subtracts the replacement(s)' resolved count from the naive `model_count` read — otherwise the base weapon is counted on every model even when some replaced it (e.g. Arkanaut Company's Privateer Pistol/Arkanaut Hand Weapon).
- **Group-level exclusive choice** (`_group_cap`/`_option_damage_score`): a `selectionEntryGroup` can itself carry the "pick N of the following" cap (rather than a per-sibling modifier) — e.g. Seraphon's Stegadon "Wargear Options" group caps Skystreak Bow *or* Sunfire Throwers to 1, not both. When a group's own cap is below its number of weapon options, only the top-`cap` options (ranked by `_option_damage_score`, via the same `engine.combat.reference_expected_damage` "N best by expected damage vs a save-4+ reference" helper `loadout.py::_apply_exclusive_choices` uses for its own free-text exclusive choices) get walked; the rest are dropped entirely rather than counted.

`_unit_wide_max` deliberately accepts *any* non-`"parent"` scope as a unit-wide cap rather than requiring an exact match to the current unit's own id — at least one catalogue entry (Kharadron Overlords' "Endrinriggers (Scourge of Aqshy)") has a copy-paste bug where the wrapper's unit-scope constraint references the *base* unit's id instead of its own, which an exact match would silently miss. Missing it would fall through to `_weapon_wielders`'s uncapped default (`max(1, model_count)`), so the wrapper's sub-weapons would inherit the *full* unit size instead of its cap — the same over-count "Nested weapon bundles" above exists to prevent.

### Intrinsic `Anti-X`/`Charge` bonuses

Ported from StatHammer's `stats.py::_intrinsic_clauses`, benefiting **both** importers: `combat.py::_intrinsic_bonus` detects `Anti-<KEYWORD> (+N <Stat>)` and `Charge (+N <Stat>)` in `Weapon.abilities` (same free-text field as the Crit tag) and folds the bonus into `attacks`/`hit`/`wound`/`rend`/`damage` before the hit/wound/save chain. `Charge` is the *only* source of a charge bonus in AoS4 (typically `Charge (+1 Damage)` on cavalry). `Anti-X` needs `Unit.keywords`; both importers populate it.

**Deliberately out of scope** (candidate for a separate, larger PR): StatHammer's Stage/Modifier/Context engine (`detect_ability_modifiers` for self-conditional unit abilities, `build_army_catalog`/`compatible_army_buffs` for cross-unit buffs, `--enable`/`--on-objective`/`--army-buff` CLI flags) — needs a full per-unit abilities table (name + description) neither aospy's schema nor either importer has today.

### Damage floor: exact distribution vs Gaussian approximation

`damage_floor66`/`damage_floor80`/`damage_floor95` (`mean − z·σ`, `_Z66`/`_Z80`/`_Z95` = inverse-normal quantiles) was
the original implementation, ported unchanged from StatHammer: it assumes the sum of hit/wound/save/ward outcomes is
approximately Gaussian, which the central limit theorem supports for many i.i.d. attacks but breaks down for the
low-attack/high-damage profiles common in AoS (monsters, single big war-machine models) — the true distribution is
discrete, bounded at 0, and often asymmetric. Concretely, a 2-attack/8-damage profile reads ~2.5 "guaranteed" damage
at 95% confidence under the Gaussian formula, but the real chance of both attacks missing exceeds 5%, so the true
95%-floor is 0 — the approximation isn't just imprecise there, it's actively optimistic.

`weapon_damage_distribution` → `unit_damage_distribution` → `distribution_floor` replace it with the *exact* discrete
distribution, no normality assumption. Since `total_attacks` is a fixed integer (not a die — see the caveat on
`engine/combat.py` above) and each attack is an independent categorical draw (miss / normal hit / crit hit, same
branches as `weapon_damage_moments`), the total-damage PMF of one weapon profile is the auto-convolution of a single
attack's outcome distribution over `total_attacks` draws; weapon profiles are independent, so a unit's PMF is the
convolution of its profiles' PMFs (mirrors `unit_damage_moments`'s variance-additivity). `distribution_floor` then
reads the quantile directly: the largest `d` with `P(damage ≥ d) ≥ coverage`. Convolution is plain Python (`list`,
no numpy) by design — `engine/combat.py` ships in the base install (`pyproject.toml` core deps = `duckdb` only;
numpy/pandas stay behind `[analysis]`) — and stays fast because PMF supports remain in the low hundreds of entries
for realistic attack counts (benchmarked ~0.6 ms/duel across the full unit database).

`orchestration/benchmark.py::_attack_damage` reads `floor66`/`floor80`/`floor95` off this exact PMF for production
use (`unit_duel`, `benchmark_attacker`, `run_all_benchmarks`, `unit_benchmark` persistence, `aospy unit stats`).
`damage_floor66`/`80`/`95` and their Gaussian machinery are kept, unchanged, purely as a comparison baseline (see
`tests/engine/test_combat.py`'s divergence/convergence tests) — nothing in the codebase still reads a floor through
them.

### Cost model (`analysis/features.py` / `analysis/cost_model.py`) — scope vs StatHammer

Ported from StatHammer's own modules, adapted to aospy's already-typed schema (no text parsing needed for `move`/`save`/`control`). `MODEL_FEATURES`/`CATEGORICAL_FEATURES` in `cost_model.py` document, inline, the rationale behind each predictor choice — read those comments before adding/removing a feature. The A/B experiments backing each choice are runnable code: `analysis/experiments/*.py` holds the ones that were adopted (each derives its "before" baseline from the current, already-adopted `MODEL_FEATURES`/`CATEGORICAL_FEATURES` rather than hardcoding a snapshot, so the comparison stays valid as those constants evolve); `scratch/experiment_*.py` keeps the ones that were tried and rejected. Three fitting strategies share `feature_frame`: `fit_cost_model` (single OLS), `fit_segmented` (separate hero/troupe regressions), `fit_cost_model_factorial` (one OLS with categorical factors + `C(is_hero):...` interaction terms — only the first two are wired to `aospy cost fit`).

Deliberately **not** ported: an ability-power axis (StatHammer's LLM-scored `ability_scores.py`) and a tactical-role ranking (`roles.py`) — aospy stores no per-unit ability text, only a free-text Crit tag per weapon. `wizard_level`/`priest_level` (from the `WIZARD (N)`/`PRIEST (N)` keywords) are the one exception, giving casters a direct — if narrow — ability-power proxy.

`CostModelResult.model` (the fitted `statsmodels` object, populated by both `fit_cost_model`/`fit_cost_model_factorial`) and `predict_one(result, features)` exist purely so `bonus_simulator/whatif.py` can predict a cost for an in-memory, not-yet-persisted `UnitFeatures` row (e.g. a unit with a bonus applied) by reusing patsy's formula-encoding rather than hand-rolling the categorical dummies. Neither is used by `aospy cost fit`/`cost residuals` or the PDF reports, which only read `coefficients`/`residuals`.

### Bonus simulator (`bonus_simulator/`) — live "what-if", no DB writes, no PDFs

A Streamlit IHM (`streamlit run src/aospy/bonus_simulator/app.py`, needs `[gui]`) lets you pick an army then a unit (two cascading dropdowns), apply a bonus — either a named army rule from `data/army_rules.json` (e.g. Stormcast Eternals' "Heure de Gloire", +1 to wound/+1 to save) or a free-form stat delta — and see the impact on that unit's profile, a live duel benchmark, and its position in the same combat×cost "best units/heroes" pantheon as `reports/best_unites.py`/`best_heros.py`, all recomputed on the fly. Nothing is written to the DB and no PDF is touched. `bonus_simulator/README.md` is the user-facing guide (launch, Streamlit's first-run e-mail prompt gotcha, how to add a rule); this section covers the internals. The whole feature — engine, orchestration and UI — lives in this one package rather than split across `engine/`/`orchestration/`/a UI package, since none of `bonus.py`/`whatif.py` is reused outside it (unlike `combat.py`/`benchmark.py`, which the rest of the codebase depends on).

- **`bonus_simulator/bonus.py`**: `StatDelta` (additive hit/wound/rend/save/ward/damage/attacks deltas) and `apply_bonus(unit, delta)` build a modified *copy* of a `Unit`/its `Weapon`s via `dataclasses.replace` — no change to `engine/combat.py` itself, since it already reads `weapon.attacks/hit/wound/rend/damage`/`defender.save/ward` directly with no intermediate "resolved profile" layer. `hit`/`wound`/`save` clamp at 2+ (best possible roll); a ward bonus on a unit with no ward grants a 6+ ward (internal convention: absent ward reads as target 7, same as `features.py::UnitFeatures.ward_num`); `weapon.name` is never touched, since `loadout.py::model_counts` matches profiles by name. `Bonus` (name + description + `StatDelta`) is the named-rule shape loaded from JSON.
- **`data/army_rules.json`** / **`bonus_simulator/army_rules.py::load_army_rules`**: hand-curated list of named army rules, same JSON-seed convention as `data/armies.json` (see below) but loaded fresh on every IHM run rather than into the DB — this list isn't fleshed out yet (only the one example above), left for incremental curation. `data/wahapedia/Faction_abilities.csv` (`type_name == "Battle Traits"`) already carries this text for every Wahapedia faction and is a natural future auto-import source, not wired up.
- **`bonus_simulator/whatif.py`**: `live_combat_row(con, unit)` duels an in-memory `Unit` against every unit in the other armies and aggregates exactly like `reports/aggregate.py` (`avg_floor_roi_pct` = mean of the 5th/34th/80th percentile of ROI across duels) — but live, via `repository.get_ranking_pool` (a DB-backed twin of `aggregate.py`'s JSON export) instead of a static snapshot file, so a hypothetical unit can be compared against the real pool without needing `scratch/per_unit_nocharge_floor66_TM.json` to exist. `rank_against_pool(con, unit)` combines that with `cost_model.predict_one` (see above) and `cost_common.combined_score` (same weights as `best_unites.py`/`best_heros.py`) to insert the unit into the troupe/hero pool and return its rank + neighboring rows. Both require the **same `DuelRules`** the CLI defaults to (`double_shoot=True, charge_move_threshold=True` — `cli/commands.py::_duel_rules`'s argparse defaults, not `DuelRules`' own dataclass defaults of `False`/`False`) to stay comparable to the persisted `unit_benchmark` pool; `whatif.RANKING_DUEL_RULES` pins this explicitly rather than relying on either default. `rank_against_pool` raises `ValueError` if `unit_benchmark` hasn't been populated yet (`aospy unit benchmark-all --charge none --attacker-mode floor66 --defender-mode mean --include-heroes`).
- **`bonus_simulator/app.py`**: uses absolute imports (`from aospy.bonus_simulator...`), not the relative imports (`from ..x`) used everywhere else in the codebase — `streamlit run` execs this file as a standalone script with no package context, so relative imports fail at runtime there specifically.

### Tournament kit (`tournament_kit/`) — roster + unit-profile PDF, no DB, no rasterization

`aospy roster pdf --list <fichier>` (needs `[roster]`) compiles a raw army-list export (`data/Proposition de listes/*.txt`, the plain-text format Warhammer Age of Sigmar: The App produces) into one PDF, in this order: a formatted cover of the list, **one merged "maison" rule card** — Battle Traits + chosen Formation + Heroic Traits + Artefacts of Power + chosen Spell Lore + chosen Manifestation Lore, all pooled together and sorted by phase band rather than one card per category (`translation/rules_resolution._resolve_rules`; falls back to a French battletome page *per category* for whatever Wahapedia doesn't cover) — the cited battle tactic cards (also "maison", verbatim French, `tactic_cards.py`), each listed unit's **"maison" warscroll card** (English, reportlab-drawn, not a copied page) plus the full warscroll of every manifestation the chosen lore can summon, and, only if something isn't covered by Wahapedia nor any battletome/Manuel du général PDF, an English appendix (see "Wahapedia fallback" below). A manifestation lore always pulls in **every manifestation it can summon**, not just its casting-rule ability — choosing the lore gives access to all of them at the table, so resolving just the "convocation" text (and not each manifestation's own warscroll) is a bug, not a size optimization; this was caught once already (see `generic_manifestation_lores` below) and is worth re-checking whenever `warscroll_index.json` is extended to a new battletome. No DB access; entirely driven by hand-curated data files plus the already-downloaded `data/wahapedia/*.csv`.

- **`tournament_kit/warscroll_card.py`**: draws a unit's profile (`render_warscroll_card`), a faction rule card (`render_rule_card` — no stat bar or weapons, abilities from every category already pooled and tagged with an origin badge by the caller, see above), or a battle tactic card (`render_tactic_card`, see below) as a compact reportlab `Table` flowable. Abilities are grouped under a **vertical phase rail** (`_PhaseRail`, a `Flowable` subclass that paints a filled rect and rotates the phase label 90° via `canvas.rotate()` — its height is measured from the group's own body table *before* the rail is built, `_ability_group_body(...).wrap(...)`, which is how a `Flowable` whose height reportlab only knows after layout gets a rotated label anyway; `_min_rail_height` floors it at the rotated label's own measured string width so a very short group can't clip it) — 7 phases from `data/Manuel du général/MdG26-27 Aptitudes.pdf` (pixel-sampled), plus an 8th green "any phase" band for reactions the CSV's `ability_phase = "Defensive reaction"` doesn't tie to one specific phase (reclassified from the ability text: mentions `Fight ability`/`combat attack` → Mêlée, `shooting attack` → Tir, otherwise → the green band; shared by every renderer via `_append_ability_groups`). A single phase group that would be taller than one page (only possible once rule-card merging pools several categories into the same phase) is split by `_chunk_group` into several same-labelled rail segments rather than overflowing. Badges (frequency, qualifier — `Your`/`Any`/`Enemy` → *Ma phase*/*Les 2 phases*/*Phase ennemi* — passive, reaction, ability keyword, weapon range/wielder-ratio, and on a rule card an extra "origin" badge folded into `keywords` via `tag_ability_origin`) are **true filled pills** (`_pill` — a small single-cell `Table` with a `BACKGROUND`/`BOX` style, since `Paragraph` alone never paints a background behind flowing text) rather than bracketed colored text — matches the original HTML design mockup, once the "rail + pill" rewrite replaced an earlier, visually weaker "horizontal band + bracketed text" compromise the user explicitly flagged as a regression from that mockup. `build_warscroll_cards_flow`/`pack_cards_two_up` pack two warscroll cards per row (list order, not sorted by height) wrapped in `KeepTogether`; rule cards and tactic cards are *not* paired this way (`_build_rule_cards_pdf`/`_build_tactic_cards_pdf`, `pdf_builder.py`) since their length varies too much for a `KeepTogether`'d pair to make sense — each is just stacked, with a tactic card individually wrapped in `KeepTogether` so two short tactic cards still land on the same page without splitting either one across it. This module supersedes unit-profile page-copying entirely — `pdf_builder.py` no longer reads unit pages from any battletome PDF, only from `wh.find_warscroll`; a unit not in Wahapedia at all is now a genuine `units_unmatched` entry. For faction rule categories it's Wahapedia-first with a page-copy fallback per category (`rules_resolution._WAHAPEDIA_RULE_CATEGORIES`, `WahapediaLookup.find_faction_category`) — the Battle Formation card is filtered to the one the list actually chose via `ParsedList.allegiance` (misleadingly named: it's literally the chosen Battle Formation's name, e.g. `"Despoilers"`/`"Warhost of Duality (20 Points)"` — confirmed against `Faction_abilities.csv`'s `subtype_name` under `type_name = "Battle Formations"`); Battle Traits/Heroic Traits/Artefacts of Power include every entry the faction has (no per-hero selection parsing yet). A Spell Lore/Manifestation Lore is treated as an ability category like any other (`rules_resolution._resolve_rules`) — Wahapedia-first via `find_faction_category`, then the French page (`find_lore_pages`/`generic_manifestation_lores`), then the English Wahapedia text block, in that order; a manifestation lore only switches to the card path if *every* manifestation it grants resolves via `find_warscroll` (else the whole thing falls back together, never half-card/half-page). Wahapedia's scraped fields carry a few corruption patterns handled by `pdf_builder._clean_html`: a truncated `<a href="...` with no closing `>` (field cut off mid-attribute), stray `%\d+`/`$\d+` single tooltip-id markers wrapping or prefixing real inline text (stripped, including a leftover `$id|` separator), and — found via a user report that one LRL Battle Trait ("Depict Rune") was missing most of its text — a **run of 2+ such ids glued back-to-back with nothing between them**, which is not decorative noise but a reference to content (here, 5 runes' individual effects) that Wahapedia resolves client-side from a tooltip table absent from all 13 downloaded CSVs: a genuine, unrecoverable data gap, not a parsing bug, so it's replaced with a visible `[texte manquant dans l'export Wahapedia — voir le Manuel du général/l'App]` note instead of silently vanishing.
- **`data/battle_tactic_cards.json`** / **`tournament_kit/translation/tactic_cards.py`**: the 6 Battle Tactic Cards for the 2026-27 season, hand-transcribed **verbatim in French** (same "no text layer, PyMuPDF-render-then-read" procedure as `warscroll_index.json`, applied to `MdG26-27 Tactiques.pdf`'s 6 pages) — same hand-curated-JSON convention as `army_rules.json`/`warscroll_index.json`, loaded fresh (`load_tactic_cards`, no DB). Unlike unit profiles/faction rules (Wahapedia, English, with a French-page fallback), tactic cards stay French and have no fallback at all: they exist in no other source. `render_tactic_card` (`warscroll_card.py`) draws each card's optional "règle spéciale" (a pre-battle setup rule 2 of the 6 cards carry) and its 3 sub-tactics (Échauffourée/Frappe/Domination, one colored pill each — reusing the same badge-severity palette as ability badges, not a new one) plus a dedicated, larger "points de victoire" pill (`_points_badge`) per sub-tactic. Replaced straight PDF-page-copying (one full page per card) entirely — `pdf_builder._build_tactic_cards_pdf` stacks the cited cards' `Flowable`s compactly enough that the common 2-cards-per-list case lands on a single page.
- Card-sheet PDFs (rule/tactic/warscroll cards) use a narrower page margin than the cover/appendix (`pdf_builder._CARD_PAGE_MARGIN`, 5.5mm vs. 18mm) — deliberately thin, to leave more of the page to the cards themselves.

- **`tournament_kit/list_parser.py`**: line-based parser for the App's stable export format (title, faction, optional allegiance, `Drops:`/lore/`Battle Tactic Cards:` header, `General's Regiment`/`Regiment N` sections of `Name (points)` lines with ` • Option` sub-lines attached to the preceding unit, an optional `Regiments of Renown` section — `Name (total points)` followed by its member unit names with no points of their own, since already included in the total — and an optional `Faction Terrain` section) → `ParsedList` dataclass. `ParsedList.base_faction` strips an Army-of-Renown suffix (`"Slaves to Darkness | Legion of the First Prince"` → `"Slaves to Darkness"`) since the base battletome is what's indexed under that name; `unique_unit_names()` folds in Regiment of Renown member units too (the regiment itself has no unit profile — see below).
- **Why the source PDFs need their own hand-built index rather than a text search**: GW's PDF battletomes (`data/Battle tome/Done/*.pdf` — `DEFAULT_BATTLETOME_DIR`; `Battle tome/A curer/` holds battletomes not yet curated into `warscroll_index.json`/`faction_rules_fr.json`, `Battle tome/Draft/` holds not-yet-adopted extras, and `Battle tome/Download GW/` holds raw downloads not yet sorted into either — all three out of scope for the index/lookup code) **and** the Manuel du général core-rules PDFs (`data/Manuel du général/*.pdf`) carry **no text layer at all** (aplatis/vectorized anti-copy treatment) — confirmed page-by-page with PyMuPDF before building anything, on both directories. `data/warscroll_index.json` is therefore curated by hand — page-render-and-look, cross-checked against the DB's already-imported canonical unit names (`unit.name`/BSData spelling, which matches the App export's unit-name spelling) for units, and against the exact English wording of a list's `Spell Lore -`/`Manifestation Lore -`/`Battle Tactic Cards:` fields for rules/cards — the exact same "hand-curated JSON, extended incrementally" convention as `data/army_rules.json` below. See the `warscroll-index` skill (`.claude/skills/warscroll-index/SKILL.md`) for the full curation procedure.
- **`data/warscroll_index.json` shape**: top-level `"factions"` (keyed by faction name) each with `"file"`, `"units"` (name → pages, each entry optionally carrying its own `"file"` override — see below), and `"rules"` — `battle_traits`/`formations`/`heroic_traits_artefacts` (single page list each, always included when present) plus `spell_lores`/`manifestation_lores` (name → pages, since a faction usually offers several and only the one a list actually cites should be pulled in — a manifestation lore's page list must include the casting-rule page *and* every one of its manifestations' own warscroll page(s), not just the former); a faction-independent top-level `"battle_tactic_cards"` (`dir`/`file` pointing at `Manuel du général/MdG26-27 Tactiques.pdf`, one page per named card — kept for provenance/tests, `find_tactic_card_pages`/`tactic_cards_path`, but no longer read by `pdf_builder.py`, which renders tactic cards from `data/battle_tactic_cards.json` instead, see above); and a faction-independent top-level `"generic_manifestation_lores"` (`dir`/`file` pointing at `Manuel du général/sorts persistants - manifestations.pdf`, `"lores"` keyed by the lore's English name, each with `"domain_pages"` — the casting-rule page(s) — plus `"manifestations"` — name → warscroll pages, one entry per manifestation that lore can summon).
- **`tournament_kit/translation/warscroll_index.py`**: loads that JSON fresh each call into a `WarscrollIndex(factions, tactic_cards, generic_manifestation_lores)` (no DB, mirrors `bonus_simulator/army_rules.py::load_army_rules`). `find_pages`/`find_tactic_card_pages` match exactly first then fall back to accent/case-insensitive (`_lookup_normalized`); `find_lore_pages`/`find_generic_manifestation_lore` additionally retry with anything from `"("` onward stripped, since a list export sometimes suffixes a lore with its point cost (`"Morbid Conjuration (20 Points)"`) that the index key doesn't carry. `GenericManifestationLore.all_pages()` concatenates `domain_pages` with every manifestation's pages — the caller always wants all of them, since picking the lore gives access to every manifestation in it, not just one. A `FactionIndex` is one battletome PDF per faction by default, but a unit's own entry can override that with its own `"file"` (`UnitEntry.file`, defaulting to the faction's `file` when absent) for a unit whose charte lives in a separate supplement rather than the base battletome — the motivating case is a small "Scourge of Aqshy" PDF covering just the 1-2 units GW released that way instead of folding them into the main book; `unit_pdf_path(index, faction, unit_name, battletome_dir)` resolves the correct PDF per unit, while `battletome_path` stays the one-PDF-per-faction shortcut for whole-faction rendering (cover, rule pages, etc.) and is unaffected by the override. Note that `find_pages`/`unit_pdf_path` aren't currently called by `pdf_builder.py` in production — unit cards are rendered from Wahapedia data (`wh.find_warscroll`, see `warscroll_card.py` below), not by copying a battletome page — so today the `"units"` list is exercised only by `tests/tournament_kit/test_warscroll_index.py`; it's still curated for completeness/provenance and in case a future page-copy path needs it again.
- **`tournament_kit/pdf_builder.py`**: `build_roster_pdf` renders a cover with `reportlab` (portrait `SimpleDocTemplate`, reusing `pdf_theme.py`'s palette — shared with `reports/common.py`, whose own `build_document` is landscape/table-oriented and doesn't fit here), then calls into `translation/rules_resolution.py::_resolve_rules`, which pools every rule category Wahapedia covers into one `render_rule_card` call and resolves the cited battle tactic cards via `tactic_cards.find_tactic_card` — `build_roster_pdf` itself then falls back to `_append_pages`-style page copying (deduplicated per source PDF — one battletome page is often a 2-unit spread) only for whatever category/lore `_resolve_rules` reports as uncovered. A manifestation lore not covered by Wahapedia is tried against two more sources in order, each its own dedup'd `PdfReader`: the faction's own battletome (its faction-specific lores), then `generic_manifestation_lores` (the shared/cross-faction lores, French, `Manuel du général/sorts persistants - manifestations.pdf`), then the Wahapedia English text-block fallback below as the last resort. Anything none of these resolve is collected into `RosterPdfResult.units_unmatched`/`rules_unmatched` and printed both on the cover page and by the CLI, never a hard failure, mirroring the importers' `skipped_*` counters.
- **`aospy roster pdf`** (`cli/commands.py::cmd_roster_pdf`) needs no `_connect(args)` — this whole feature is DB-free by design. Missing `[roster]` prints the same "install this extra" message pattern as `cmd_cost_fit`'s `[analysis]` check.
- Companion units that ride along a paid entry for free (e.g. Slaves to Darkness' "Singri Brand"/"The Oathsworn Kin" bundled with "Gunnar Brand") are merged away in the aospy DB (see "Composite/companion unit merging" above) but still appear as their own named lines in the App's list export — `warscroll_index.json` indexes them under their own name directly (not derivable from the DB), separately from the merge logic.

#### Wahapedia fallback (`tournament_kit/translation/wahapedia_lookup.py`) — English appendix for what's in no PDF at all

Regiments of Renown (a different AoS4 concept from the "Army of Renown" supplements above), Army-of-Renown-only units/rules, and generic cross-faction *spell* lores used across the sample lists are absent from `data/Battle tome/` and `data/Manuel du général/` (confirmed by reading every page of both). They *are*, however, already present in English in the Wahapedia CSV export the `wahapedia` importer already downloads (`data/wahapedia/*.csv`, itself text — no curation/page-hunting needed, unlike the PDFs above). The 6 generic cross-faction *manifestation* lores (`Twilit Sorceries`, `Aetherwrought Machineries`, `Krondspine Incarnate`, `Forbidden Power`, `Primal Energy`, `Morbid Conjuration`) were in this same boat until the user supplied a scan specifically for them (`Manuel du général/sorts persistants - manifestations.pdf`, French, resolved via `generic_manifestation_lores` above, tried before this Wahapedia fallback) — this Wahapedia path stays as the catch-all for anything even that scan doesn't cover:

- Generic lores live under the pseudo-faction `faction_id == "EnS"` (Endless Spells) in `Faction_abilities.csv`, keyed by `subtype_name` (e.g. `"Twilit Sorceries"`) — `find_generic_lore` groups its rows by `line`.
- An Army of Renown's own rules (Battle Traits/Heroic Traits/Artefacts of Power/Spell Lore/Manifestation Lore, all of them) live under its own `type_name` (e.g. `"Legion of the First Prince"`) in the same file, this time distinguished by `subtype_name` as the *category* — `find_renown_army_rules` groups by that. Its member units are stored in `Warscrolls.csv` under their bare name (`"Legion of the First Prince Bloodletters"` in a list export is just `"Bloodletters"` in Wahapedia) — `pdf_builder.py` retries the lookup with the renown-name prefix stripped before giving up. **The categories an Army of Renown carries *replace* the base faction's equivalents** rather than supplementing them (e.g. "Legion of the First Prince" replaces Battle Traits/Heroic Traits/Artefacts of Power/Spell Lore/Manifestation Lore, but not Battle Formations — it has none of its own) — `rules_resolution._AOR_REPLACES` maps each `_STATIC_RULE_SECTIONS` attribute to the `subtype_name`(s) that supersede it, and `_resolve_rules` omits the base battletome page for any category the chosen Army of Renown actually replaces, so the PDF never shows both the superseded French page and the replacement English one side by side.
- A Regiment of Renown is its own `Warscrolls.csv` row (`role == "Regiment of Renown"`, no stat line of its own) with composition in `Warscrolls_organisation.csv` and its own bonus ability in `Warscrolls_abilities.csv`, both keyed by that row's `id` — `find_regiment_of_renown` assembles the three. Several near-duplicate rows exist (one per faction allowed to take it); the one with a non-empty `legend` is its faction of origin and is preferred. Its member units (e.g. Skarbrand, native to Blades of Khorne) are then resolved the normal way via `find_warscroll`, which searches *all* factions, not just the list's own. When a Regiment of Renown has exactly one member (e.g. "The Exiled One" = Skarbrand alone) and that member is itself rendered via the Wahapedia English fallback, `pdf_builder._build_wahapedia_appendix_pdf` skips the separate "Regiment of Renown — X" section and folds the regiment's own ability straight into that unit's card instead (`_render_warscroll(..., regiment_note=..., extra_abilities=...)`) — a one-member "regiment" and "the unit" read as the same thing, no need for two structures. A regiment with several members still gets its own section as before.
- `pdf_builder._clean_html` converts Wahapedia's markup (`<a href>` unwrapped, `<span class="kwb...">` → `<b>`, `<ul><li>` → bulleted `<br/>`-separated lines) into what `reportlab.platypus.Paragraph` accepts; `_safe_paragraph` falls back to fully tag-stripped plain text on any parse error, because this CSV snapshot is scraped external data and at least one field is truncated mid-tag (`Faction_abilities.csv`'s `"FIRST-DAMNED PRINCE"` battle trait) — never let one malformed row crash the whole PDF.
- Everything resolved this way is rendered on its own clearly-labelled "ANNEXE — CONTENU WAHAPEDIA (ANGLAIS)" pages appended at the very end of the PDF (never interleaved with the French battletome content) and listed in `RosterPdfResult.wahapedia_used` — a deliberate choice (confirmed with the user) not to machine-translate rules text, to avoid a mistranslation misleading someone about actual game rules.

#### Roster modes (`build_roster_pdf(..., mode=...)` / `aospy roster pdf --mode ...`)

Everything described above is the `hybrid` mode (default, unchanged historical behavior). 3 more variants exist, selected by one `mode` argument threaded through `_resolve_rules`/`build_roster_pdf` (`RosterMode`, defined in `translation/rules_resolution.py` and re-exported by `pdf_builder.py`) and gating every per-category resolution the same way:

- **`en`**: Wahapedia only — the French battletome-page-copy fallback tier (`_STATIC_RULE_SECTIONS`, and the French-page tiers of the spell-lore/manifestation-lore chains) is simply skipped (`_resolve_rules`'s `allow_page_copy = mode == "hybrid"`); anything Wahapedia doesn't cover shows up as a plain `RosterPdfResult.rules_unmatched`/`units_unmatched` entry, never an interactive prompt — the CLI run itself never blocks waiting on input. (A separate, conversational workflow — comparing Wahapedia's English data against an actual battletome/faction-pack scan and asking for a missing page when a real gap turns up — is a curation/audit concern, not something this mode's plumbing does; out of scope for `pdf_builder.py` itself.)
- **`fr`**: like `en` (no page copy) but every Wahapedia-resolved category also passes through `data/faction_rules_fr.json` (`translation/faction_rules_fr.py`, see below) via `rules_resolution._fr_patch`, which corrects/completes the pool wherever a curated French entry exists for that faction/category/unit — a faction with nothing curated yet degrades naturally to the same result as `en`, no special-casing needed.
- **`fr-extended`**: `fr` plus one more rule card, "Aptitudes Génériques — MdG26-27" (`data/generic_core_abilities.json` / `tournament_kit/translation/generic_core_abilities.py`, a loader twin of `season_rules.py` for the *complete* `MdG26-27 Aptitudes.pdf` rather than just its page-5 season rules) — omitted entirely (not an empty card) while that file stays unpopulated.

**`data/faction_rules_fr.json`** / **`tournament_kit/translation/faction_rules_fr.py`**: hand-curated French verbatim for a faction's rule categories (`battle_traits`/`formations`/`heroic_traits_artefacts`/`spell_lores`/`manifestation_lores`/`prayer_lores`, same names as `_STATIC_RULE_SECTIONS`/`data/warscroll_index.json`'s `rules` keys) *and* per-unit ability text (`factions.<name>.units.<unit>.abilities`), transcribed from a battletome ("BT"), a faction pack ("FP", a faction's provisional rules before its battletome ships) or a seasonal supplement like Scourge of Aqshy ("Aqshy") — same hand-curated-JSON convention as `warscroll_index.json`/`army_rules.json`, empty (`{"factions": {}}`) until a faction is actually curated (STD/LRL are the first two planned, deferred to a later session — see the `faction-rules-fr` skill). Each JSON entry is either a **patch** of an existing Wahapedia ability (`wahapedia_name` set to Wahapedia's exact English name — the join key `pdf_builder.apply_fr_overrides` matches on; only `name`/`description` are overridden, every other field — `condition`/`ability_phase`/`points_type`/`points` — stays whatever Wahapedia already had, no need to re-transcribe mechanically-derived fields) or a **standalone addition** (no `wahapedia_name`/no match — e.g. genuine Scourge-of-Aqshy content Wahapedia doesn't carry at all — in which case `condition`/`ability_phase` must be hand-filled with the same internal English mini-vocabulary `season_rules.json` already uses, never shown as-is). `formations`/`spell_lores`/`manifestation_lores`/`prayer_lores` entries carry a `scope` field (the formation/lore name) so only the option the list actually chose applies (`get_faction_category_overrides(..., scope=...)`, same `split("(", 1)[0]` normalization as `WahapediaLookup.find_faction_category`'s `subtype_name` filter); `battle_traits`/`heroic_traits_artefacts` have no `scope` (every entry applies, mirroring Wahapedia). A standalone addition is only meaningful for `manifestation_lores` as a *patch* — `_resolve_rules` resolves each summonable manifestation's warscroll (`find_warscroll` on the `"SUMMON <name>"` prefix) *before* applying French patches, precisely so a patch can't rename that join key out from under the lookup; a from-scratch manifestation ability would have no warscroll to attach to. Each patched entry also carries a `provenance` object (`bt_text`/`errata_patch`/`errata_source`) recording the original battletome text and, if the ability was touched by a "MISES À JOUR DE RÈGLES" errata page, the correction as printed — kept purely for audit/re-curation, never read by `rules_resolution.py`/`pdf_builder.py` (`description` already holds the final corrected text that gets rendered). `rules_resolution._apply_ability_text_overrides`/`_ABILITY_TEXT_OVERRIDES` (the older, single-entry ad hoc fix for one corrupted Wahapedia field, LRL's "Depict Rune") is unrelated and still applies in *every* mode, unconditionally — it now runs *after* `_fr_patch` specifically so a future `faction_rules_fr.json` entry for that same ability can still match Wahapedia's pristine English name; once such an entry exists, the legacy override simply becomes a no-op for it since the name it looks for is already gone.

### Data files vs generated files

`data/armies.json` and `data/compositions.json` are hand-authored seed data (loaded by `seed.py`/`aospy init`). `data/army_rules.json` is the same kind of hand-authored data but for the bonus simulator's named army rules (loaded by `bonus_simulator/army_rules.py`, not `seed.py` — never touches the DB). `data/warscroll_index.json` is the same kind of hand-curated data again, this time mapping unit/rule/generic-manifestation-lore name → PDF page (see "Tournament kit" above); `data/battle_tactic_cards.json` (`tournament_kit/tactic_cards.py`) is the same convention once more, for the 6 Battle Tactic Cards' full verbatim French text (no PDF page mapping needed any more, tactic cards are drawn, not copied). `data/faction_rules_fr.json` (`tournament_kit/faction_rules_fr.py`) is the same convention for the `fr`/`fr-extended` roster modes' per-faction verbatim/errata/season-content layer (see "Roster modes" above) — empty (no faction curated) as of this writing. `data/generic_core_abilities.json` (`tournament_kit/generic_core_abilities.py`) is `season_rules.json`'s sibling for `fr-extended`'s extra card (the complete `MdG26-27 Aptitudes.pdf` rather than just its page-5 season rules) — also empty as of this writing. `data/Battle tome/*.pdf` and `data/Proposition de listes/*.txt` are the source PDFs/list exports `tournament_kit` reads, not generated. `data/Manuel du général/*.pdf` holds several independent source PDFs read the same way: `MdG26-27 Tactiques.pdf` (transcribed once into `battle_tactic_cards.json` above, kept as the source of truth) and the generic manifestation lores (`sorts persistants - manifestations.pdf`, user-supplied, French) among them. `data/wahapedia/*.csv` is the Wahapedia data source (same files as the StatHammer project; re-download to refresh). `data/aospy.duckdb` (default DB path) and everything under `scratch/` (ad hoc aggregation/PDF-report scripts, e.g. `scratch/build_pdf.py`) are generated/exploratory, not source — PDF/JSON outputs from those scripts land in `scratch/output/`, kept out of the scripts themselves.
